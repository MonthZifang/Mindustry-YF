# YZF 插件与依赖边界审计

## 结论

YZF 的依赖和插件使用同一套 `module.hjson`、运行时和调用 API，但它们不是同一类交付物：

- **依赖/模块**放在 `config/yzf/modules/<author>/<directory>/`，服务于多个业务模块，不应出现在插件商城。
- **插件**放在 `config/yzf/plugins/<directory>/`，面向一个可选的玩家、管理或运营场景，可以在插件商城安装、启用、禁用和重载。
- **核心网络模块**放在 `config/yzf/netmods/`，由网关启动独立进程，不是 JS、Java 或 Kotlin 插件。

目录是运行时的权威边界。`loadType` 是元数据兼容字段，不能替代目录；商城只展示 `_source=plugins` 的模块。

## 已归入通用依赖的模块

| 模块 ID | 目录 | 归类理由 | 主要消费者 |
|---|---|---|---|
| `yueyu-hud` | `modules/monthzifang/yueyu HUD` | HUD、弹窗、欢迎、公告和队列等可组合 UI/消息能力 | 状态栏、Help 及其它业务模块 |
| `generic-vote-service` | `modules/monthzifang/通用投票服务` | 统一投票生命周期和结算回调 | 地图加载、换图、投票管理 |
| `web-yfui-adapter` | `modules/monthzifang/WEB YFUI Adapter` | HTTP、鉴权、插件页面和通用模块网关 | WEB YFUI 与所有 Web 插件 |
| `web-yfui` | `modules/monthzifang/WEB YFUI` | 面板宿主页面，不承载单一玩法 | Adapter |
| `yueyu-help` | `modules/monthzifang/HIK help` | 跨插件帮助注册和命令目录 | 投票管理、迁移模块及其它插件 |
| `yfm-api-expose` | `modules/monthzifang/YFM API Expose` | 开发者 API 命名空间和动态访问层 | 开发/调试模块 |

这些模块保留独立目录和完整文档，但不会被 `/api/plugins` 或插件商城当作可安装业务插件。

## 目前修复的边界问题

1. 6 个通用能力已从 `plugins/` 移到 `modules/monthzifang/`，避免依赖出现在插件市场。
2. `WEB YFUI` 显式依赖 `monthzifang/web-yfui-adapter`，面板宿主与 HTTP 适配层的启动顺序由依赖解析保证。
3. 插件商城只处理业务插件；依赖模块仍能被运行时解析，但不会提供“安装插件”按钮。
4. 每个模块目录都有 `DEVELOPMENT.md`，文档中的 API 以实际入口、导出函数或 HTTP 路由为准；没有稳定 API 的模块会明确标注“无公开 API”。

## 判断标准

一个模块若同时满足“被多个模块复用、提供稳定接口、没有单一玩法目标”，应放入 `modules/`。一个模块若主要注册玩家命令、管理页面、单个业务流程或外部平台行为，应放入 `plugins/`。不能因为它使用 Java、JS 或 Kotlin 就改变这个判断。
